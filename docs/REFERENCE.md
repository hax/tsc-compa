# tsc-compa 技术参考

编写适配器、读取指标文件或修改运行器时，可以在这里查参数、字段和比较规则。
各项设计的来由和报告的用途见 [设计思路](DESIGN.md)；
支持情况见 [实现状态](STATUS.md)，执行命令见 [README](../README.md) 和 [CI 使用说明](CI.md)。

本文记录现有代码的行为。warning 兼容比较、完整结果与 T0 回归门槛分离的新方案，
见 [设计思路](DESIGN.md) 和 [待实现工作](STATUS.md#53-新的诊断比较与回归策略待实现)。

## 1. 配置与编译选项

### 1.1 参考配置

通过 `--baseline` 选择的参考配置由以下部分组成：

| 字段 | 作用 |
| --- | --- |
| `id` | 通过 `--baseline` 选择的名称 |
| `tsc` | 参考 tsc 的可执行文件路径 |
| `baseArgs` | 用于现场生成期望的基础 CLI 参数 |
| `corpus` | 语料引用的配置键 |
| `manifest` | 默认用例清单 |

参考 tsc 的版本与语料版本是两个独立维度，必须明确配对。
同一个参考 tsc 可以对应不同测试用例或清单，每种组合用一个配置名选择。

语料引用可以是版本标签或固定提交；需要稳定复现时应优先使用固定提交。
读取官方诊断基线时，应核对语料提交与参考编译器发布来源的关系；
具体配置、版本默认值和测试框架差异见 [实现状态](STATUS.md)。

### 1.2 参考诊断来源与运行模式

这两个 CLI 参数控制不同的事情：

| 维度 | 参数值 | 作用 |
| --- | --- | --- |
| 参考诊断来源 `--expectation-source` | `tsc` | 运行参考 tsc，生成并缓存参考诊断 |
| 参考诊断来源 `--expectation-source` | `official-baseline` | 读取官方 `.errors.txt` 中的参考诊断 |
| 运行模式 `--mode` | `official` | 将支持的用例编译选项指令交给适配器 |
| 运行模式 `--mode` | `fixed` | 使用适配器声明的 `fixedOptions`，不使用用例编译选项指令 |

`official` 表示遵循用例选项，不表示一定读取官方诊断基线。
两种期望来源都可以与 `official` 模式组合。

`fixed` 模式用于验证固定选项检查器的调用流水线，要求适配器声明 `fixedOptions`。
读取官方诊断基线时，模式或额外参数不会重新生成基线内容；
修改被测选项后，不应假定保存的期望仍与输入配置一致。

字段 `meta.verdictEligible` 表示运行模式和适配器是否满足门禁的比较条件：

```text
mode = official 且 adapter.supportsOptions = true
```

门禁要求此字段为 true；用例完成数量和错误数量另行检查。

### 1.3 选项来源与优先级

运行参考 tsc 时，基础参数写明目标版本的官方测试框架默认值，避免依赖不同版本
CLI 的隐含默认值。基线配置的默认值只作用于期望侧，不自动强加给被测实现。

CLI 参数按以下顺序构造，支持的用例选项追加在最后：

| 接收方 | 参数来源，按追加顺序 |
| --- | --- |
| 生成参考诊断的 tsc | `baseline.baseArgs` → `--base-arg` → 用例选项或 `fixedOptions` |
| 被测适配器的 `CaseInput.args` | `--base-arg` → `--adapter-arg` → 用例选项或 `fixedOptions` |
| 读取官方诊断基线 | 使用已保存的内容，不执行上述参数生成 |

适配器还可以在调用实现时添加自己的默认参数或输出格式参数。
同一选项重复出现时，应遵循目标 CLI 的解析规则；用例选项追加在最后，
可能覆盖先追加的同名参数，包括 `--base-arg`。

`CaseInput.options` 是结构化选项列表；`CaseInput.args` 是供 CLI 使用的参数列表。
前者不包含所有基础参数，后者也不包含待写入的源文件路径。
适配器需要结合结构化选项、CLI 参数和自身默认值处理输入。

跨版本比较需要说明目的：

- 使用各自默认值：衡量默认行为差异；
- 显式对齐选项：尽量区分默认值差异与检查行为差异。

对齐选项前应确认双方都支持这些选项和值。
标准库、模块环境和测试框架差异另见 [实现状态](STATUS.md)。

## 2. 执行流程

```text
语料引用 + 用例清单 + 基线配置 + 适配器
                    │
              读取与解析用例
                    │
              构造虚拟文件与选项
                    │
              分类、过滤与支持检查 ──► SKIP + 原因
                    │
       ┌────────────┴────────────┐
       ▼                         ▼
  获得期望诊断               调用被测适配器
  ├─ 参考 tsc + 缓存          └─ 统一结果
  └─ 官方诊断基线
       │                         │
       └────────────┬────────────┘
                    ▼
           诊断匹配 + 一致性分档
                    ▼
          指标、逐案明细与可选报告
                    ▼
          防退步检查与可选兼容性门禁
```

流程图表示数据依赖，不要求两侧并行执行。
任何阶段未能形成可比较结果，都应记录跳过或异常原因。
报告保留门禁检查结果及失败信息。

## 3. 用例解析、选择与分类

### 3.1 指令与虚拟文件

官方测试输入通过注释指令声明选项和虚拟文件，例如 `// @strict: true`、
`// @target: es2015`、`// @filename: a.ts`。
`@filename` 划分虚拟文件；被识别为元数据的指令行不属于源文件内容。
剥离哪些行会影响诊断位置，因此解析行为必须与所选语料的测试框架核对。

指令处理分为四类：

| 类别 | 行为 | 结论限制 |
| --- | --- | --- |
| 支持的选项指令 | 转换为结构化编译选项 | 仍需确认被测实现接受该选项 |
| 跳过指令 | 整个用例记录为 SKIP，并给出原因 | 不进入诊断统计分母 |
| 忽略指令 | 不转换为选项，保留忽略记录 | 不代表该指令对诊断或文本一定无影响 |
| 未知或不可解析指令 | 整个用例记录为 SKIP | 不在不完整输入条件下给出比较结论 |

整理文件名、将虚拟文件写入临时目录时，需检查路径是否越出用例根目录。
绝对虚拟路径、声明文件和多配置变体需要分别判断，不能混为一种“不支持”。
指令支持表、扩展名规则及保真度缺口见 [实现状态](STATUS.md)。

### 3.2 用例选择与多维标签

用例清单固定样本和顺序；扫描语料只是发现候选用例，不能代替说明测试范围。
类型检查用例以 `compiler` 和 `conformance` 套件为主要对象；
IDE、工程构建等用例应使用独立的测试口径。

分类标签用于描述多个维度：

| 维度 | 标签示例 |
| --- | --- |
| 套件 | `suite:compiler`、`suite:conformance`、`suite:other` |
| 文件数 | `files:single`、`files:multi` |
| 语言特征 | `lang:js`、`lang:jsx` |
| 输入形态 | `shape:parser` |
| 选项涉及的功能 | `options:module`、`options:lib`、`options:emit` |
| 环境依赖 | `env:skip` |
| 运行时期望特征 | `expect:syntax`、`expect:no-errors` |

不同维度的标签可以重叠；`suite:*` 等同一维度内的互斥标签可组成分区。
`byClass` 的数字不能跨重叠标签直接相加。

`--exclude-class a,b` 命中任意一个标签即排除；
`--only-class a,b` 要求同时命中所有指定标签。
运行期标签要在获得期望之后才能判断。
被排除的用例记录为 SKIP，原因为 `类排除:<tag>`，不会从结果中静默消失。

## 4. 参考诊断

### 4.1 运行参考 tsc

将虚拟文件写入临时目录后，由参考 tsc 检查。
解析器将 CLI 输出的 1-based 行列转换为接口中的 0-based 行列。
诊断文件路径应映射回用例内相对路径，不把临时目录或外部环境文件混入用例诊断。

缓存按虚拟文件路径与内容、参数及参考 tsc 版本构造键。
缓存用于复用相同输入的结果；
更换二进制或环境时，还需检查缓存标识是否足以区分此次变更。
异常处理、语法错误筛选及缓存实现位置见 [实现状态](STATUS.md)。

### 4.2 读取官方结果文件

读取 `.errors.txt` 时，只解析第一个以 `====` 开头的行之前的诊断摘要块。
后面的源码标注不是诊断摘要，不参与 T3 比较。

基线查找需适配目录布局，候选顺序为：

1. 保留用例相对目录；
2. 保留套件首段目录，将其下的子目录压平；
3. 只按用例文件名在基线根目录查找。

例如 `conformance/es6/Symbols/Foo.ts` 可以对应
`conformance/Foo.errors.txt`，而不是仅尝试完整相对路径。
布局和配置变体命名是不同问题，不能通过“找不到文件”替代变体支持。

对支持范围内、且已正确映射到完整基线集合的用例，框架将找不到 `.errors.txt`
解释为期望零诊断：无错用例也需要参与误报检查。
这是依赖官方基线生成约定的解释规则，不是“磁盘上缺文件必然证明没有错误”。
不完整语料或错误路径映射会产生错误期望，必须单独排查。

## 5. 诊断匹配与指标

### 5.1 诊断字段与统计范围

诊断接口包含：

| 字段 | 含义 |
| --- | --- |
| `file` | 用例内相对文件路径 |
| `line`、`col` | 0-based 行号和列号 |
| `code` | 数值诊断码，如 `2322` |
| `severity` | `error` 或 `warning` |
| `message` | 可选的诊断首行文本 |
| `width` | 可选的诊断跨度；不参与本文定义的匹配和分档 |
| `fullText` | 可选的单条诊断完整文本块，包括说明续行 |

误报、漏报、错锚和诊断覆盖率只统计 `error`。
T0–T2 分档使用完整诊断列表，包含 `warning`，因此两组结果的统计对象并不相同。
错误统计和 T0–T3 等级分别记录这些结果。

### 5.2 匹配规则

对错误诊断按以下顺序匹配：

1. 按 `(file, code)` 分组；
2. 组内按 `(line, col)` 做多重集匹配，得到精确命中；
3. 将剩余期望和实际诊断各取一条配对，计为错锚；
4. 未配对的实际诊断计为误报，未配对的期望诊断计为漏报。

“多重集”表示同位置同诊断码重复出现的条数也参与比较，不能先去重。
错锚配对不使用文本或距离寻找语义对应关系，因此只是差异归类规则，
不能据此断言两条诊断表达了相同的检查结论。

下例位置为便于阅读使用的 1-based 行列：

| 期望诊断 | 实际诊断 | 归类 |
| --- | --- | --- |
| `a.ts(1,1) TS2322` | `a.ts(1,1) TS2322` | 精确命中 |
| `a.ts(2,1) TS2345` | `a.ts(3,1) TS2345` | 错锚 |
| `a.ts(4,1) TS2304` | 无 | 漏报 |
| 无 | `a.ts(5,1) TS7006` | 误报 |

结果为：期望 3 条、实际 3 条、命中 1 条、错锚 1 对、漏报 1 条、误报 1 条；
诊断覆盖率为 `1 / 3`。错锚会降低覆盖率，但不重复计入误报或漏报。

### 5.3 指标定义

下表省略重复的 `totals.` 前缀；除用例总数和跳过数外，统计只包含形成可比较结果的用例：

| 字段 | 单位／定义 |
| --- | --- |
| `cases`、`ran`、`skipped` | 本次用例数、完成比较的用例数、跳过的用例数 |
| `expectTotal`、`hitTotal` | 期望错误诊断数、精确命中的错误诊断数 |
| `coverage` | `hitTotal / expectTotal`；期望总数为零时是 `null`，不是 100% |
| `fpCases`、`fpTotal` | 至少有一条误报的用例数、误报诊断条数 |
| `missTotal` | 漏报诊断条数 |
| `misanchorCases`、`misanchorTotal` | 至少有一对错锚的用例数、错锚配对数 |
| `passCases` | 误报、漏报、错锚均为零的用例数；不要求 T2 或 T3 一致 |
| `fpFreeCases` | 误报为零的用例数；仍可能有漏报或错锚 |
| `byTier` | 每个用例最高一致性档位的分布，不是累计达档数 |
| `messageMismatch` | 文件、位置和诊断码命中但首行文本不同的期望错误诊断条数 |
| `t3Failures` | 存在官方基线正文时，T3 未达原因的分类计数 |

其中 `cases` 和 `skipped` 包含跳过用例，其余诊断统计不包含。
`byClass` 按标签聚合，`byCode` 给出误报／漏报的高频诊断码；
`skips` 按原因汇总跳过，`samples` 保存文本差异、T3 未达等样例。

对错误诊断，匹配结果满足：

```text
期望总数 = 精确命中数 + 漏报数 + 错锚配对数
实际总数 = 精确命中数 + 误报数 + 错锚配对数
```

误报使用用例数和诊断条数两个计数。
报告高覆盖率时，应同时给出 `ran / cases`、跳过原因及样本选择方式。
崩溃、超时或不支持的用例排除于诊断分母之外，会影响结果的代表性。

## 6. T0–T3 匹配等级

### 6.1 等级定义

每个用例只记录达到的最高档位，后一档包含前一档的条件：

| 档位 | 标识 | 比较内容 |
| --- | --- | --- |
| 未达 T0 | `none` | 诊断位置与码的多重集不同 |
| T0 | `location` | `(file, line, col, code)` 多重集相同 |
| T1 | `category` | T0 条件，加 `severity` 相同 |
| T2 | `text` | T1 条件，加首行 `message` 相同 |
| T3 | `full` | T2 条件，加诊断摘要文本相同 |

T0–T2 不比较诊断输出顺序；缺失的 `message` 按空串处理。
报告中的“至少达到 T1”由 T1、T2、T3 三档相加得到，
不同于 `byTier.category` 单独记录的“最高只达到 T1”。

### 6.2 T3 的文本范围与换行处理

期望侧取官方基线第一个 `====` 之前的摘要块，将换行统一为 LF，
去除摘要末尾的空白行，保留其他行内及行尾空白。
比较对象不是整个基线文件的原始字节。

实际侧按以下优先级获得摘要文本：

1. 适配器提供的 `CaseOutcome.fullText`；
2. 按实际输出顺序拼接 `Diagnostic.fullText`；
3. 未提供单条完整文本时，渲染文件、位置、严重级别、诊断码和首行文本。

适配器应输出与期望侧摘要形态一致的文本。
补充说明（elaboration）、相关诊断信息（related information）和输出顺序都影响 T3。
如果官方摘要只有首行，回退渲染也可能达到 T3；
如果包含续行，则仅提供首行通常不足以达到 T3。

没有官方基线正文时，非空诊断最多评到 T2；两侧诊断为空且实际摘要为空白时，
按约定记为 T3。这是无错用例的特例，不是对缺失正文做了完整文本验证。
现场生成期望的报告不能把这类档位解释为“与官方基线全文一致”。

T3 未达原因分为 `missing`、`extra`、`diagnostics`、`order`、
`elaboration`、`related`、`other`，分别描述诊断少报、多报、集合不同、
顺序不同、说明续行不同、关联信息不同及其他差异。

## 7. 回归检查与 CI 通过条件

### 7.1 ratchet 规则

防退步清单按“被测实现 × 基线配置”隔离，避免不同实现共享同一个最低档位要求。
TSV 中每行记录 `<case id><TAB><tier>`，只登记至少达到 T0 的用例。

清单只存门禁档位 T0–T2，T3 在读入和写回时归一为 T2：

```text
full → text：不是退步
text → category：退步
已登记用例在本次结果中变为 SKIP：退步
```

防退步检查针对本次结果中的用例。
仅从本次用例清单中移除某个已登记用例，不等同于记录它为 SKIP，
也不会自动完成该用例的回归检查。因此维护者必须同时审阅用例清单的变化。

### 7.2 初始化与更新

| 场景 | 行为 |
| --- | --- |
| 非门禁运行，`--ratchet-impl` 推导的文件不存在 | 自动初始化，仅登记本次达到的门禁档位 |
| 非门禁运行，显式 `--ratchet` 文件不存在 | 默认报错；可通过 `--ratchet-init` 初始化 |
| 非门禁运行，已有清单 | 改善可写回，退步导致非零退出；已有最低档位不因退步而降低 |
| 门禁运行 | 要求清单文件已存在且非空，不自动初始化，也不写回改善 |

`--ratchet` 与 `--ratchet-impl` 二选一。
清单应由维护者审阅后提交入库；运行器检查文件是否存在及是否非空。
首次建立清单时记录当前通过情况，后续运行以此检查回归。

### 7.3 CI 检查

启用 `--gate` 后，以下检查全部通过才算门禁通过：

| 检查 | 条件 |
| --- | --- |
| 运行资格 | `meta.verdictEligible = true` |
| 执行 | 至少一个用例完成比较 |
| 防退步 | 配置清单时，清单非空且本次无 T0–T2 回落 |
| 数量阈值 | 误报／漏报／错锚不超过对应显式或默认上限 |
| 覆盖率阈值 | 配置了下限时，覆盖率可计算且不低于下限 |

没有防退步清单时，三个数量上限默认为零；
配置清单后，数量上限默认不检查，由逐案档位约束，也可叠加显式阈值。
`--gate-max-fp`、`--gate-max-miss`、`--gate-max-misanchor`、
`--gate-min-coverage` 必须与 `--gate` 一起使用。

T3 仅报告，不参与防退步或门禁失败判定。
门禁也不默认要求全部选中用例完成比较，不能将“门禁通过”解释为“所有用例通过”。
失败时退出码非零，逐项检查结果写入 `meta.gate`。
实际 CI 矩阵与阈值见 [CI 使用说明](CI.md)。

## 8. 适配器接口与批量协议

### 8.1 统一接口

适配器实现 `Adapter.check(CaseInput) → CaseOutcome`，
并可提供初始化和关闭方法。

| 字段／形态 | 含义 |
| --- | --- |
| `per-case` | 逐案调用实现进程 |
| `batch` | 一个常驻进程处理多个用例 |
| `api` | 接口预留的进程内调用形态 |
| `supportsOptions` | 适配器声明是否接受外部编译选项，不是运行时协商结果 |
| `fixedOptions` | 固定选项模式使用的结构化选项列表 |

`CaseOutcome.status = ok` 表示获得了可比较的检查结果，不表示没有错误诊断。
`skip`、`crash`、`timeout` 在汇总中记为 SKIP 并保留原因，不进入诊断统计分母。

适配器可通过 `CaseOutcome.fullText` 提供 T3 摘要文本，
通过 `CaseOutcome.checkMs` 提供 Check 阶段耗时，单位为毫秒。
各适配器提供哪些字段，见 [实现状态](STATUS.md)。

### 8.2 NDJSON 消息

批量协议通过 stdin 接收请求、stdout 输出响应；
每行是一个完整 JSON 对象，诊断日志写到 stderr。
协议版本字段为 `protocol: 1`。

请求示例，每行可独立解析：

```jsonl
{"protocol":1,"type":"check","id":"case-1","files":[{"path":"a.ts","text":"const value: string = 1;\n"}],"options":[{"name":"strict","value":true}],"args":["--strict","true"]}
{"protocol":1,"type":"shutdown"}
```

响应示例，`result.id` 回显对应请求的关联 ID：

```jsonl
{"protocol":1,"type":"hello","implementation":{"name":"checker","version":"1.0.0"}}
{"protocol":1,"type":"result","id":"case-1","status":"ok","diagnostics":[{"file":"a.ts","line":0,"col":6,"code":2322,"severity":"error","message":"Type 'number' is not assignable to type 'string'."}]}
{"protocol":1,"type":"result","id":"case-2","status":"skip","diagnostics":[],"skipReason":"@jsx"}
{"protocol":1,"type":"result","id":"case-3","status":"crash","diagnostics":[],"message":"checker process failed"}
```

`case-2` 和 `case-3` 分别演示 skip 与 crash 请求结果。
关联 ID 必须唯一；它用于匹配请求与响应，不必等于语料中的用例路径。
诊断 `file` 使用请求中的虚拟文件路径，行列使用 0-based，
`severity` 未提供时客户端按 `error` 处理。

`hello` 可提供实现名称和版本，不改变 `supportsOptions`。
收到 `shutdown` 后实现应结束进程。
现有客户端消费的字段及扩展限制见 [实现状态](STATUS.md)。

## 9. 性能指标

### 9.1 测量对象与抽样

`--perf-ratio` 在兼容性运行中附带性能测量，不为耗时设置兼容性门禁。
正常用例执行时记录 `adapter.check` 从开始到结束的实际耗时，不为计时额外重跑被测用例；
但参考侧执行和空程序测量仍有额外成本。

固定样本按套件、行数分桶及期望错误特征分层，并用固定种子排序选取。
这些特征是抽样依据，不保证覆盖所有诊断码或所有语言特性。
两侧每个样本各运行一次，参考先执行与实现先执行的顺序对半分配，
减少时间窗口造成的系统性偏差，不等于消除了测量噪声。

参考侧使用逐案 tsc CLI；实现侧沿用所选适配器，不自动转换成逐案进程。
两侧采用对应的用例选项，但还需检查适配器附加参数、进程模式和并行度是否一致。
跨实现比较必须公开这些条件。

### 9.2 比值与计算条件

主比值的方向始终是“被测实现耗时 / 参考 tsc 耗时”：
小于 1 表示在该测量口径下被测实现耗时更少，不表示它完成了等价的全部工作。

- 两侧样本均提供 Check 阶段耗时时，使用累计 Check 耗时之比；
- 否则使用扣除空程序固定成本估计后的实际耗时之比；
- 分子或分母非正、固定成本占主导等情况返回 `null` 并记录原因。

Check 耗时只衡量检查阶段；实际耗时还可能包含启动、写入文件、解析、绑定和输出，
比较时需使用相同的测量方法。

性能附录另给错误诊断完全匹配子集的比值，该子集要求误报／漏报／错锚均为零，
不要求 T2 或 T3 一致。结果同时记录样本组成、逐案比值聚合和不对称条件告警。
抽样默认值、空程序重复次数和具体字段见 [实现状态](STATUS.md)。

## 10. 结果输出与外部集成

`metrics.json` 保存运行元数据、聚合指标及可选门禁／性能结果；
`details.json` 保存逐案诊断和差异，供归因使用。
Markdown 和自包含 HTML 报告从同一份数据渲染，不再执行测试。

报告应同时呈现运行配置、完成／跳过数量、误报／漏报／错锚、
诊断覆盖率、一致性档位和结论限制。
前后运行的差异只有在语料、用例选择、参数与比较规则可对照时才有明确意义。
渲染过程应具有确定性，HTML 内容需转义，失败信息不能因汇总而丢失。

CI 可以接收外部实现构建出的二进制，再交给适配器执行。
分发渠道、下载权限和触发方式属于部署配置，不改变诊断比较规则。
报告产物、分支保护配置及二进制接入操作见 [CI 使用说明](CI.md)。
