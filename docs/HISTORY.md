## 2. 关键修正与结论边界

### 2.1 默认值漂移与跨版本结果

早期对 6.0／7.1 默认 target 的判断来自标准库加载观察，曾写为 ES2015；
核对官方源码后，改为相应版本的 `LatestStandard`。
strict 等默认值也随版本发生变化。

因此跨版本差异不能全部归为检查语义差异。
参考侧与候选侧参数被分离，并提供显式对齐选项的比较方式。
具体默认值和数据见 [RESULTS.md 结论 2](RESULTS.md#结论-2版本默认值来自官方测试框架59--60-发生变化)。

### 2.2 缺基线与错误路径映射

TS7 Go 布局并非所有测试类别都保留完整子目录。
早期漏掉测试类别目录内平铺路径，把部分 conformance 用例解释为没有错误结果文件，
导致参考结果为空、各候选均出现同样的多报错误。

修正查找顺序后，这类差异消失。
该问题说明「缺 `.errors.txt` → 参考结果为零诊断」依赖完整测试集和正确映射，
不是可以脱离前提使用的证明规则。

### 2.3 T3 从首行比较转向摘要文本

诊断对象的首行不能表达完整的说明续行、关联信息和输出顺序。
T3 增加适配器完整文本支持，并将比较范围限定为第一个 `====` 前的摘要块。
原先首行解析导致的未达情况与真实诊断差异由此分开归因。

当时 T3 仅用于报告，回归门禁最高到 T2。
旧清单的 `full` 条目归一为 `text`，避免文本渲染支持变化被误用为新的门禁要求。
样本结果及归因见 [RESULTS.md](RESULTS.md) 的结论 10、11。

### 2.4 来源对齐没有消除残留差异

审计曾怀疑 6.0.3／TS7 的官方测试集提交与 npm 发布来源不一致，
是已记录多报错误、漏报及 T3 未达的原因。
2026-11-16 将提交对齐后，对同一批样本复跑，指标没有变化。

这推翻了「固定提交漂移解释这些样本残留差异」的假设。
相关样本在两套提交中内容相同，残留项归因于测试框架保真度：
pretty、UTF-16、emit 指令、续行路径、截断选项、无冒号指令行等。
该结论只针对已检查的样本，不能推断两套提交的全部测试集相同。
证据见 [RESULTS.md 结论 11](RESULTS.md#结论-11官方测试集提交对齐-npm-githead-后的复跑v12026-11-16)。

- `DESIGN.md`：设计原则、术语、配置维度、协议、匹配规则、指标和结论边界；
- `STATUS.md`：具体版本、实现位置、支持范围、已知限制与待办；

- `DESIGN.md` 从选择检查器的问题出发，用例子解释各项设计为什么需要、怎样帮助判断；
- `REFERENCE.md` 保留参数、字段、匹配规则、适配器协议及计算方法，供接入和维护时查阅；
- 术语在使用时解释；当时曾在主文末尾保留名称小表，后续精简时移除。
  详细比较规则移至 `REFERENCE.md` 第 11 节，主文保留设计概览和取舍。

## 4. 诊断策略与回归门槛的调整（方案）

后续讨论提出，候选检查器可以把新增发现作为 warning，也可以升降原有诊断的严重级别。
因此设计拟将诊断发现、严重级别和附加诊断分开比较，并保留严格对照全部输出的方式。

回归最低要求与记录内容也分开：默认回归门槛采用 T0，
完整比较结果仍保留，T1–T3 的变化通过报告查看。

进一步讨论将这些变化改为独立差异项，保留「兼容」和「严格一致」两档。
两档都要求主诊断的文件和起点相同；兼容档允许等价码及其他诊断信息差异，
严格一致则要求全部诊断信息、数量和输出相同。
回归默认保持兼容，报告继续展示各项变化。

两档比较和回归检查后来已实现，当前行为和限制见[实现状态：两档比较与回归](STATUS.md#53-两档比较与回归)。
