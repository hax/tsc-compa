# tsc-compa 的设计思路

tsc-compa 把同一批代码交给候选检查器和指定版本的 tsc，比较诊断结果，
帮助你判断是否值得替换项目中的类型检查器，并在升级时发现回归。

## 1. 我们想帮助你做什么决定

尝试一个更快的检查器时，速度之外还有几件事要确认：

- 现有代码会不会多出报错，原来能发现的错误会不会被放过；
- 报错位置、严重级别和文字改变后，编辑器、诊断快照或解析脚本需要改什么；
- 后续版本能否保持已经验证过的行为。

所以报告分别呈现这些差异，而不是只给一个总兼容率。
测试聚焦类型检查诊断；生成 JavaScript、声明文件和 IDE 功能需要各自的验证方式。

## 2. 用官方测试作为共同起点

测试输入主要来自 TypeScript 官方测试集。它包含大量针对具体语言行为的小用例，
能覆盖泛型库、声明文件和复杂推导中的组合；发现差异后，也比从整个工程里找原因容易。

测试范围由明确的用例列表确定，并可按语言特性、编译选项和文件结构分类筛选。
冒烟测试先发现明显问题，评估候选时再围绕项目需要的功能扩大范围。
报告按这些分类展示结果，便于看清问题集中在哪一部分。

官方小用例检查语言行为，真实工程验证配置和依赖的组合。选检查器时，先做官方用例对照，再用工程验证。

## 3. 一次比较是怎么来的

### 3.1 让两边拿到同一个问题

用例除了代码，还可能包含多个文件和编译选项。测试先读出这些输入，
再取得双方诊断、匹配对应关系，最后生成报告和回归结果。

适配器处理不同检查器的调用与输出，让比较逻辑可以复用。设计包含三种调用方式：

| 调用方式 | 怎样测试 | 取舍 |
| --- | --- | --- |
| 逐案二进制 | 每个用例准备文件，启动检查器命令并收集输出 | 容易接入已有 CLI，用例较好隔离，但反复启动进程有成本 |
| 批量二进制 | 常驻进程连续接收用例 | 适合大规模测试，需要批量输入协议 |
| 进程内 API | 在运行器中调用检查器 API | 便于传递结构化诊断，需要适配 API 并管理进程内状态 |

候选可以来自本地构建、安装包或外部 CI 的产物，源码不必放在本仓库。
这三种方式使用相同的测试输入和比较规则；构建分发和调用协议见 [技术参考](REFERENCE.md)
及 [CI 使用说明](CI.md)。

### 3.2 两种参考结果：运行 tsc，或读取官方输出

`--expectation-source` 决定参考结果从哪里来：

- 运行选定版本的 tsc，便于换版本或调整选项后对照。`tsc` 使用 CLI，并缓存相同输入的结果；
  `ts7-api` 则用 TypeScript 7 的结构化 API，可直接取得诊断范围等字段；
- `official-baseline`：读取官方 `.errors.txt`，省去生成参考结果的工作，也能核对测试工具
  是否正确处理了用例和环境。

运行参考检查器适合试验配置，读取官方保存的结果可帮助区分检查器差异与测试运行器差异。

### 3.3 先对齐版本和选项

项目使用哪个 tsc 版本，通常就先选哪个作为参考。版本的默认选项可能不同：
同一段代码开启 `strict` 后多出报错，原因可能是设置，而非类型推导。

比较时要区分两个目的：使用各自默认设置，观察默认行为差异；
或显式对齐支持的选项，继续比较相同条件下的检查行为。
评估实际迁移时，按项目的 `tsconfig` 设置比较。

`official` 运行模式使用用例选项；候选只能接受固定选项时，可用 `fixed` 模式先验证接入。
正式评估要确认候选接受了本次用例的选项。运行模式与参考结果来源是两个独立选择。

每次运行记录参考版本、测试集版本、用例列表、选项和候选版本或文件哈希，
让其他人能复现，也能查清前后差异来自检查器还是输入变化。

## 4. 先看问题是否找到，再看它是 error 还是 warning

诊断先按文件、起点和诊断码找对应，再分别比较严重级别、范围、文字和附加信息。
原 error 改成 warning，记为降级，而不是漏掉了这条诊断。

少数码表达同一种问题，只是建议不同。例如 TS2339 表示属性不存在，
TS2551 在此基础上附带修正建议。兼容比较按明确的等价码列表匹配，
原始码和建议文字的差异继续保留。

候选也可能把更强的分析结果作为附加 warning，或在确认代码安全后将原 error 降级。
因此报告要分开说明：参考诊断是否找到、严重级别怎样变化，以及新增了哪些诊断。
具体差异的原因再结合用例判断。

## 5. 两档比较：兼容与严格一致

- **兼容**：参考诊断都能在同一文件、同一起点找到对应，诊断码相同或为已确认的等价码。
  允许严重级别、标记范围、文字、related info 和输出顺序不同，也允许附加 warning；
  漏掉参考诊断或新增未匹配的 error 则不兼容。
- **严格一致**：全部诊断信息和输出相同，诊断不多不少，包括 warning。

两档都要求主诊断的文件和起点相同。其他差异独立记录，报告默认展开不同的项；
严重级别不一致时，仍继续比较文字和范围。
严格一致需要完整诊断信息，字段可用性及逐项规则见 [技术参考](REFERENCE.md#11-两档比较与回归判定规则)。

这两档服务不同目的：兼容档关注原有检查和定位能否保持，
严格一致档关注诊断输出能否直接替换。选哪档作为回归要求，由使用场景决定。

## 6. 工具自检和跳过记录

先让同版本 tsc 自比，排查调用和解析问题；再对照官方结果，核对用例读取和测试环境。
这样能减少把测试工具的问题当作候选检查器问题的情况。

超出测试范围、依赖缺失或超时的用例记录为未完成，并附原因。检查器崩溃或超时不作为允许的跳过，门禁会失败。
报告同时给出完成和跳过数量，便于判断项目需要的功能是否测到了，而不只看覆盖率。

## 7. 怎样把已经做到的兼容性保留下来

回归记录保存已经验证过的用例和要求，后续运行逐案对照。
这个持续保护机制叫 `ratchet`（棘轮）：修好新用例时，旧用例也要继续接受检查。

每个候选和参考配置分别保存记录。维护者审阅初始结果，确定保护哪些用例、选择哪档要求；
更换参考版本或测试范围时，再审阅和更新。
原始诊断、两档结果与各项差异都保留，回归识别与门禁处理分开。

**从严格一致退到仅兼容，也是回归。** 报告明确列为严格一致性回归，并给出具体差异。
本仓库默认保护兼容档；项目若需要锁住完整诊断输出，可以选择严格一致档：

| 退步 | 兼容档门禁 | 严格一致档门禁 |
| --- | --- | --- |
| 严格一致 → 仅兼容 | 记录回归，兼容要求仍满足 | 失败 |
| 兼容 → 不兼容 | 失败 | 失败 |

固定回归用例要持续运行，未完成的用例也要报告。
具体记录、字段回归和门禁判定规则见 [技术参考](REFERENCE.md#11-两档比较与回归判定规则)；
现有命令见 [CI 使用说明](CI.md)。

## 8. 在同一批输入上比较性能

先看兼容结果，再比较耗时，并单独给出兼容通过的用例子集。
固定抽样并保留样本组成，交替安排双方执行顺序，减少输入和先后顺序造成的偏差。

Check 阶段耗时主要反映类型检查；实际耗时还包括启动、文件处理、解析、绑定和输出。
因此报告同时说明测量方法与调用方式，便于判断收益来自检查还是进程复用。
比值使用「候选耗时 / 参考 tsc 耗时」，小于 1 表示候选在该测量中更快。
抽样和计算细节见 [技术参考](REFERENCE.md#9-性能指标)。

## 9. 拿到报告之后，怎样判断是否值得采用

先确认参考版本和测试范围，再看不兼容用例及严格一致性的差异，
判断哪些会影响项目的检查、编辑器定位或诊断解析。性能则与计划采用的调用方式一起看。

最后在真实工程中并排运行，核对配置、依赖、退出码和构建输出；
决定采用后，将选定的回归要求接入 CI。

`metrics.json` 给出聚合指标，`details.json` 保留逐案明细，
Markdown／HTML 从同一份数据生成。脚本可以读取指标，人工审阅可以从摘要进入具体用例，
再与之前的结果对照。

执行命令见 [README](../README.md)，支持范围见 [实现状态](STATUS.md)，
对照数据见 [实验结果](RESULTS.md)，设计演进见 [HISTORY.md](HISTORY.md)。
