# 文档写作与审读

## 先想清楚读者

- `DESIGN.md` 面向使用 TS 工具链、评估是否采用 tsc 兼容实现的工程师。
  讲清设计是什么、怎样使用、为什么需要、怎样帮助判断；字段和协议细节放到技术参考。
- `REFERENCE.md` 面向接入检查器、读取结果或维护测试框架的工程师。
  便于查参数、字段和精确规则，使用示例说明；无需重复设计文档的完整叙述。
- `STATUS.md` 面向了解项目能力和后续工作的使用者与维护者。
  先说明现在能做什么、还有哪些影响使用的问题，再给版本、任务和实现位置。
- `HISTORY.md` 面向想理解重要取舍和历史修正的读者。
  说明原问题、观察和选择，不把提交日志逐条改写成流水账。
- `RESULTS.md` 面向比较实现、评估实验或复现结果的工程师。
  说明输入、条件、结果及如何解读；保留历史日期和数据。
- `CI.md` 面向运行或接入 CI 的工程师。
  先说明哪个任务做什么、何时触发和如何操作，再解释配置与排错。

新增文档或安排审读时，根据文档用途选择读者角色，不默认所有读者都了解项目内部实现。

## 写清楚，再解释理由

- 先用简短说明或例子交代“是什么、怎么用”，再回答“为什么这样设计”。
- 让设计叙述沿着“实际问题 → 做法 → 理由与取舍 → 对读者的用途”展开。
- “CI”“参考版本”“报告”等名称要指明对象，避免在不同场景中省略主语。
- 术语在首次使用时解释；必要时保留英文名并给出自然的中文说明。
- 多写动作和具体后果，少用抽象口号、翻译腔或自造行话。
- 不靠反复列举“不能证明什么”来体现严谨。影响使用的限制应写清触发条件和下一步做法。
- 技术参考可以更细，但准确的规则也应写成读者能直接理解的中文。

## 审读看什么

- 读者审读：能否回答该角色实际关心的问题？哪里需要先懂内部细节才能继续读？
- 中文审读：严格检查难懂术语、生硬翻译、空泛用途、重复免责和不地道的表达。
- 将审读发现落实为具体修改，不以链接有效、术语扫描通过代替可读性判断。
- 对尚在讨论的设计选择，先与用户对齐，再写成确定的规则。
